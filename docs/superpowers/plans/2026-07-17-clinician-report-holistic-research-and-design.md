# Holistic Clinician Report — Research & Product Design

**Author context:** User request: "I want a very holistic report ... when i submit the report to doctor, that he will understand exactly what has happened." Framing the pain precisely: in the consult room, the patient can't reliably *reconstruct* what happened, what triggered it, when sleep collapsed, what the episode looked like — but NilaMind has been *tracking all of that* on-device in real time, more reliably than memory (F1, F6). This plan turns that already-existing tracking into a *doctor-readable* artifact, and proposes additional capture-time changes so less is lost in the first place.

**Scope:** Research + product design only. **No code, no implementation, no schema changes.** Implementation follows sign-off, then enters the queue at `docs/PLAN_OF_ACTION.md` per the repo protocol.

**Status: draft, awaiting owner review.**

## 3. Design rules (NilaMind golden-rule preservation)

All proposals in §4 below must pass these invariants, or they are not built:

1. **Wellness, never therapy.** No copy or computed claims using "therapy / therapist / treat / diagnose / cure." Every section is *the patient's self-report*, not NilaMind's verdict. Every algorithmic aggregation must be either (a) pure counting of fields the patient wrote, or (b) a validated instrument the patient answered, or (c) an explicit deterministic format that the patient could regenerate by hand.
2. **§9 / safety is unchanged.** Crisis safety floor stays in `safety.ts`; MiniLM classifier unchanged; output gate Rules 1–6 unchanged; nothing in this plan touches the crisis path. Risk *events* may be listed; risk *scores / risk levels / risk recommendations* must never be produced — per F11, F12, F13, F14.
3. **Nothing leaves the device by default.** Every aggregation runs in-process. Exports are still user-initiated, still on-device→share-sheet.
4. **Privacy promise preservation.** No raw Nila chat transcripts reach the PDF (the existing report does not include them; this mustn't change — chat frequently contains §9-sensitive content and the patient did not consent to clinical sharing of unedited LLM conversation).
5. **On-device determinism.** Every aggregation is pure-function on already-stored device data. No ML model runs against aggregated streams. The on-device Gemma model's job remains the chat, not the report.
6. **Personalisation = memory-into-context, model stays fixed.** Same as the rest of the app. The PDF generation is template-driven, not LLM-written.
7. **18+ only.** No structural change to age-gate.
8. **The patient is the data principal.** All redaction controls proposed give the patient *more* power over what leaves the device, not less.
9. **WIRE WHAT YOU BUILD.** Any new engine must reach a user surface in the same change. The 2026-07-16 plan flagged the prior dead-wiring problem; this plan does not regress it.

## 5. HOW to include — display & determinism rules

The whole PDF generator is already deterministic and pure. New items in §4 must keep that promise. Below are the design rules any implementation has to follow:

### 5.1 Determinism

- Every aggregation is a pure function inside `src/services/` taking JSON-serialisable inputs from already-decrypted `secureLocal`.
- No ML calls during report generation. Lifesaving rule: never route aggregation through the on-device LLM.
- All seconds/zone-aware math uses the same `toUtcMidnight` helper already in `clinicianCharts.ts:84`; no timezone drift.

### 5.2 Wellness-not-therapy language lock

- Every section's title is descriptive ("What I logged") — never diagnostic ("Diagnosis" / "Likely condition").
- Every computed number is *paired with its source-of-truth*. Example: if A2 shows "avg intensity 4.6", it must say "(from 23 check-ins, X missed days)" — no orphan numbers.
- Every correlation must be paired with its sample size and the warning text "weakly/none/moderately correlated" so the clinician cannot overread. (F12)

### 5.3 No computed risk levels

- **Per F11/F13/F14, never replace the removed risk gauge / temporal-risk score with a new "level" or "category"**. We surface events (a deterministic list of dates and types) and *recommend the clinician ask about them*, never label them.

### 5.4 LLM does not write the report

- Risk: LLM is non-deterministic, hallucinates clinical claims, can invent context. **Banned.** Even prose formatting must be template-driven.
- The single optional LLM use is *paraphrasing-redacted* diary/journal lines the patient explicitly opts to share. This is opt-in, only when the patient types "share this with my doctor" on a specific entry, never automatic. (Stays well within the patient's authority.)

### 5.5 Consent redaction must be by-category, not all-or-nothing

- The P19 caregiver preferences pattern (`caregiverPreferences`) is the model. Per-category toggles, default on, persisted in `secureLocal`.
- Two pre-built profiles the patient can pick in one tap: *Minimal* (mood + sleep + date-stamped safety-plan existence flag — no other content); *Full* (everything).
- Profile + per-category overrides saved into `exportAudit` so the patient remembers what they last shared.

### 5.6 Cover page + integrity

- Cover page: a fixed template the PDF layer renders first, before content. Includes:
  - patient-typed identifier (or `no identifier` for max privacy)
  - generation timestamp (device clock + UTC offset)
  - period (`Week ending`, `Month ending`, `Quarter ending`, or custom)
  - section list actually included (per the toggles above)
  - SHA-256 of the rest of the PDF content
  - disclaimer block (inline copy of `clinicianReport.ts` line-9 disclaimer + a one-paragraph "wellness self-report" framing)
  - the consent toggle answers (e.g., "name redacted" / "diary included")
- Integrity hash: SHA-256 of the post-cover, post-table-of-contents content, computed in JS. Cover page renders the hash and labels it "Verify with shasum on this file after download to confirm no edits."

### 5.7 Patient's pre-visit note

- Two-minute typing-or-voice (Vosk already wired) affordance before the PDF generates. Stored in `secureLocal` keyed by `nilamind_visit_note_<ISO_DATE>`. Last 4 visits kept.
- Template prompts (user-editable, never required):
  - "Three things I want remembered"
  - "Questions I want to ask"
  - "What's changed since the last visit"
- Appended to the PDF as Section 1 (after cover, before data sections) — *only if the user saved a note*.

### 5.8 SI / safety-plan policy (no regression)

- The 2026-07-16 redesign removed the crisis-detection-performance block + temporal risk score; with this plan we do not re-add them in any form. We do not generate "suicide risk" categories.
- Safety-plan *state* (B2) is content the patient wrote; it is *the patient's plan*. Revealing it requires per-category redaction default-off for sensitive sections (means-counseling block: not auto-included unless category toggled on; if it is toggled on, the patient sees a single confirm step: "this will reveal what means you plan to remove").

### 5.9 Chart additions (PCORI / F15 / F16)

- Per F16, comparison anchors beat raw numbers. New charts added with these rules:
  - Always paired with a textual descriptor ("Sleep: 7 days logged in window, 4 between 6-8 h; trough 3.5 h on 2026-07-08.")
  - Threshold lines drawn if a published clinical threshold exists (e.g., WHO-5 cutoff ≤13 shows the "low wellbeing" band — *Topp 2015*, not proprietary).
  - Min-trend-points gate (`MIN_TREND_POINTS=3`, already in `clinicianCharts.ts:21`) applies to every new series — sparse data is shown as points, not connected lines.

### 5.10 i18n

- Every new section uses `i18n` keys like `cr_*` (clinician report). Confirmed en/hi/ta/te at parity per `PLAN_OF_ACTION.md` invariant §5.
- New translations handled in the same change as the feature.

### 5.11 Test seams

- Every pure aggregator (§4 B1–B12, §4 C1–C2, §4 D1–D4) gets its own `*.test.ts` per `AGENTS.md` TDD rule.
- The cover-page integrity hash gets a known-input → known-output test (so a coverage ID is stable across renames).
- The patient-pre-visit note module gets an end-to-end test that pipes a note into the report-input builder and asserts the note appears verbatim in the rendered report.

## 9. What this plan explicitly does *not* propose

To bound scope and keep the doc honest:

- **No cloud sync / no clinician-facing portal.** Self-export is the patient's power; a cloud sync would put NilaMind into the regulated-clinic-software bucket, undoing the privacy promise and reopening the [F14] FDA Non-Device CDS question. (P19 caregiver share deliberately stays user-initiated for the same reason.)
- **No new clinical scales built by us.** We never invent clinical items — we either reuse validated instruments (PHQ-9, GAD-7, WHO-5) or we don't measure. (Hard rule from `AGENTS.md`.)
- **No LLM-written clinical narrative.** Per §5.4.
- **No risk score, level, category, gauge, or recommendation.** Per [F11, F12, F13, F14] and the just-landed 2026-07-16 redesign.
- **No removal of the existing `temporalRiskAssessment.ts` or `crisisSafetyValidation.ts`.** The 2026-07-16 plan flagged those as orphaned; deletion is the owner's call, not implicit.
- **No automatic / mandatory PDF re-generation on a cadence.** The user decides when to share.
- **No PII beyond what the user types.** No analytics, no account creation, no third-party network call.
